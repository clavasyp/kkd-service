# Требования: модуль ККД

Что делает решение и как это проверить. Точные условия, формулы, поля и таблицы описаны в [design.md](design.md): ссылка «раздел N» ведёт туда. Причины решений собраны в разделе 12.

| Метка источника | Что значит |
|---|---|
| задание | Прямо написано в задании Backend. При расхождении главнее всего остального |
| mock | Так сделано в mock API из задания Frontend. Это подсказка, а не требование |
| наше решение | Задание молчит, выбрали сами |

## 1. Назначение

Сотрудники заносят цели и ключевые результаты (КР) в корпоративную систему управления целями, и если данные заведены некорректно, целеполагание работает неэффективно, а руководство не видит реальной картины. Сервис модуля контроля качества данных (ККД) проверяет цели и КР по правилам, хранит результаты прогонов в PostgreSQL и отдаёт через REST API метрики с учётом каскадирования, найденные проблемы и дельту с прошлым прогоном. API рассчитан на разработчика фронтенда страницы ККД: все значения приходят готовыми, без расчётов на клиенте. Страницей пользуются администраторы системы, руководители департаментов и ответственные за целеполагание в подразделениях, проверка планируется еженедельно.

## 2. Границы

**Входит:** схема БД с миграциями и откатом, стартовые данные, 4 правила отдельным компонентом, выполнение прогонов, три GET-метода, единый формат ошибок, тесты, сквозная проверка, запуск одной командой, спецификация в `specs/`.

**Не входит:** страница ККД и любой фронтенд, авторизация и роли, методы сверх трёх GET, запуск прогонов по расписанию, правила `GOAL_NO_OWNER` и `KR_NO_TARGET`, таблица сотрудников, статус дельты в строке проблемы и список исправленных проблем, `limit` и `offset` у `GET /api/runs`, несколько значений в одном фильтре, поиск, сортировка по выбору клиента. Полный список с причинами: раздел 13.

**Известные ограничения:** раздел 14.

## 3. Функциональные требования

### 3.1. Схема БД

**FR-1. Предметные таблицы.** `unit` с иерархией, `goal` и `key_result` с полями и допустимыми значениями из раздела 2.1. *Источник:* задание (подразделения, ответственный, родитель, статус, срок, целевое и фактическое значение, вес, дата факта), mock (значения `status`, имена `unit_id` и `level`), наше решение (`title`, `measure_unit`, `key_result.goal_id`, `goal.unit_id`, `goal.level`).

**FR-2. Плохие данные можно занести.** Поля, которые правила проверяют на пустоту, допускают `NULL`, у `weight` нет `CHECK`, тип `NUMERIC(6,2)` (раздел 2.1). *Источник:* наше решение.

**FR-3. Таблицы результатов.** `kkd_rule`, `kkd_run`, `kkd_issue` (раздел 2.2). Число проблем в колонках не хранится, оно считается из строк `kkd_issue`. *Источник:* задание (справочник, прогон, проблема), mock (значения `status`), наше решение (ключ, копии на дату прогона, `enabled`).

**FR-4. Снимки.** `goal_snapshot` и `key_result_snapshot` хранят состояние всех целей и КР на дату прогона, в том числе закрытых целей (раздел 2.3). *Источник:* наше решение, таблицы сверх перечня задания.

### 3.2. Прогон

**FR-5. Запуск прогона.** Прогон запускается появлением строки `running` в `kkd_run`: из стартовых данных или вставкой SQL. Его подхватывает `RunPoller` внутри сервиса. GET-методы ничего не пишут и прогоны не считают (разделы 6.1, 6.2). *Источник:* наше решение.

**FR-6. Выполнение прогона.** `RunProcessor` одной транзакцией снимает снимок, если его нет, вызывает компонент правил, выбирает базу сравнения, записывает проблемы и ставит `completed` (раздел 6.2). *Источник:* наше решение.

**FR-7. Сбой прогона.** Ошибка логики или данных даёт `failed` с постоянным текстом в `error`, повторов нет. Отсутствие таблицы, потеря связи с базой, взаимная блокировка и падение сервиса оставляют прогон `running` (раздел 6.3). *Источник:* наше решение.

**FR-8. Повторяемость результата.** Возраст факта считается только от `snapshot_date`. Перезапуск сервиса не пересчитывает прогоны `completed`. Правка текущих `goal` и `key_result` не меняет ответы по завершённым прогонам. *Источник:* наше решение.

### 3.3. Правила

**FR-9. Отдельный компонент.** Логика правил живёт в пакете `ru.kkd.domain.rules`, не знает о Spring, SQL и HTTP, получает данные и возвращает список найденных проблем. На каждое правило свой класс (раздел 10). *Источник:* задание (компонент), наше решение (класс на правило).

**FR-10. Четыре правила.** Реализованы `GOAL_NO_KR`, `KR_WEIGHTS_SUM`, `CASCADE_NO_PARENT`, `KR_STALE_PROGRESS` с условиями из раздела 4. Они применяются только к активным целям и их КР. *Источник:* задание (коды, важность, область действия), mock (значение «активная», часть случаев), наше решение (выбор набора, остальные случаи).

### 3.4. Стартовые данные

**FR-11. Состав.** Три подразделения, от 20 до 30 целей, два прогона со снимками. В каждом прогоне есть нарушения каждого из четырёх правил, второй прогон сравнивается с первым (раздел 3). *Источник:* задание (объём, нарушения, есть с чем сравнивать, `HQ-CIB`), наше решение (остальные коды и даты).

**FR-12. Дефекты, которые не дают проблем.** В данных есть неактивные цели с дефектами, цель с пустым `owner_name` и КР с пустым `target_value` (раздел 3.2). *Источник:* наше решение.

**FR-13. Результаты считает компонент правил.** Миграция не пишет `kkd_issue`. После наката оба стартовых прогона имеют статус `running`, а строки проблем появляются после расчёта в сервисе. *Источник:* наше решение.

**FR-14. Контрольные числа.** После расчёта API отдаёт числа из раздела README [«Контрольные числа стартовых данных»](../README.md#контрольные-числа-стартовых-данных). README единственный документ с контрольными числами. `scripts/check-chain.sh` при запуске разбирает его таблицы и сверяет все строки, своих чисел в скрипте нет, при расхождении главнее README. Названия подразделений, даты прогонов и базу сравнения скрипт так же берёт из таблиц README и сверяет с базой и ответами API. *Источник:* наше решение.

**FR-15. Чего нет в стартовых данных.** Неуспешного прогона, прогона, который остаётся выполняющимся после расчёта, подразделения без целей и переноса цели. Эти случаи покрыты тестами, а неуспешный и выполняющийся прогон и подразделение без целей ещё и проверками AC-13...AC-15. *Источник:* задание («два прогона», «в двух-трёх подразделениях»), наше решение (перенос).

### 3.5. Запуск и миграции

**FR-16. Запуск одной командой.** `docker compose up` поднимает PostgreSQL, миграции со стартовыми данными и сервис. Файл `.env` не нужен. Повторный запуск с тем же томом не применяет миграции заново и не создаёт дублей (разделы 9.2, 9.4). *Источник:* задание (одна команда), наше решение (работа без `.env`).

**FR-17. Инструмент и исполнитель.** Миграции написаны на Liquibase, у каждого changeset есть откат. Накат и откат выполняет только контейнер `migrate` (разделы 9, 9.1). *Источник:* задание (Liquibase или Flyway с откатом), наше решение (отдельный контейнер).

**FR-18. Цепочка накат → откат → повторный накат.** Проходит без ошибок, команды в разделе 9.3. `docker compose down -v` это сброс базы, а не откат. *Источник:* задание (цепочка), наше решение (откат до пустой схемы).

**FR-19. Другие проверки отката.** Откат только стартовых данных и проверка всех откатов на пустой базе (раздел 9.3). *Источник:* наше решение.

**FR-20. Сервис во время цепочки.** Сервис не падает и не требует перезапуска, между откатом и накатом отвечает 503, после наката сам считает прогоны заново, и ответы совпадают побайтно с ответами до отката (раздел 9.4). *Источник:* наше решение.

### 3.6. API

**FR-21. Общие правила.** Есть ровно три метода: `GET /api/runs`, `GET /api/kkd/summary`, `GET /api/kkd/issues`. Имена полей, `null`, даты и неизвестные параметры: раздел 8. *Источник:* задание (три метода, пример формата), наше решение (неизвестные параметры).

**FR-22. `GET /api/runs`.** Список прогонов: статус, дата снимка, с каким прогоном сравнивается, число проблем (раздел 8.2). *Источник:* задание (состав), mock (имена полей, обёртка), наше решение (`null` у незавершённого прогона).

**FR-23. `GET /api/kkd/summary`.** По `run_id` и `unit_id` отдаёт `run`, `compared_to`, `unit`, `metrics`, `issues_by_severity`, `delta` (раздел 8.3). *Источник:* задание (формат), mock (`higher_is_better`), наше решение (расчёт при запросе).

**FR-24. Метрики.** Три метрики `clean_goals_share`, `issues_total`, `cascade_coverage` с текущим и прошлым значением, дельтой и признаком «лучше / хуже», количественные и качественные, с учётом каскадирования (раздел 5). *Источник:* задание (минимум три, `clean_goals_share`, каскадирование), mock (формулы), наше решение (что считать качественным и количественным).

**FR-25. Ветка подразделения.** Метрики, разбивка, счётчики дельты и фильтр `unit_id` в списке проблем считаются с учётом дочерних на любую глубину (разделы 5, 7, 8.4). *Источник:* задание («с учётом дочерних»), mock (способ подсчёта, фильтр с дочерними).

**FR-26. Округление, дельта метрики и `trend`.** По разделу 5. *Источник:* задание (признак «лучше / хуже», значение `worse`), mock (значения `same`, `better` и логика), наше решение (округление, дельта из округлённых).

**FR-27. Разбивка по важности.** `issues_by_severity` всегда содержит три строки (раздел 5). *Источник:* задание (разбивка и поля), mock (три строки всегда, постоянный порядок).

**FR-28. Первый прогон.** Если базы сравнения нет, прошлые значения и дельта равны `null`, а не 0 (раздел 5, пример в разделе 8.3). *Источник:* задание, mock (случай с неуспешными прошлыми прогонами).

**FR-29. Подразделение без целей.** Сводка и список проблем отвечают 200, доли равны `null`, счётчик 0 (раздел 5). *Источник:* mock, наше решение.

**FR-30. `GET /api/kkd/issues`.** Список проблем прогона с фильтрами по подразделению, правилу и важности, пагинацией `limit`, `offset`, `total` и постоянным порядком. `offset` за концом списка даёт 200 и пустой `items`. Поля строки: раздел 8.4. *Источник:* задание (фильтры, пагинация), mock (имена, значения по умолчанию, фильтр с дочерними), наше решение (`id` строки, значения на дату прогона, порядок).

### 3.7. Дельта

**FR-31. Та же проблема.** Проблема та же самая, что и в прошлом прогоне, если совпадают правило и объект. Текст `details` в сравнение не входит (раздел 7). *Источник:* задание, наше решение (`details`).

**FR-32. База сравнения.** Последний успешно завершённый прогон перед текущим, неуспешные и выполняющиеся пропускаются (раздел 6.4). *Источник:* mock (пропуск неуспешных), наше решение (запись в `compared_to_run_id`).

**FR-33. Счётчики дельты.** `new`, `persisting`, `resolved` с отнесением к подразделению по разделу 7. *Источник:* задание (счётчики), mock (смысл `resolved` и вернувшейся проблемы), наше решение (подсчёт по всей организации).

### 3.8. Ошибки и параметры

**FR-34. Единый формат и коды.** Ошибки имеют вид `{"error": {"code": "...", "message": "..."}}`, сообщения на русском, без стека и имён классов Java. Статусы и коды: раздел 8.5. *Источник:* задание (формат, 404, 422), mock (часть кодов), наше решение (405, 503, 500, неизвестный путь, 400 на испорченный адрес, который пропускает Tomcat, прочие клиентские статусы Spring MVC).

**FR-35. Параметры.** Допустимые значения, граница 404 и 422 и порядок проверок: раздел 8.1. Первая найденная ошибка в форме параметров приводит к 422. *Источник:* задание (имена `run_id`, `unit_id`, `limit`, `offset`, статусы), mock (остальные имена, значения по умолчанию, предел 200), наше решение (обязательность, порядок).

**FR-36. Неуспешный и выполняющийся прогон.** `summary` и `issues` отвечают 409 `RUN_FAILED` и 409 `RUN_IN_PROGRESS` (раздел 8.5). `GET /api/runs` показывает такие прогоны (раздел 8.2). *Источник:* mock.

### 3.9. Тесты

**FR-37. Обязательный минимум.** JUnit 5, минимум 4 сценария: два правила на граничных данных, расчёт метрики, расчёт дельты. HTTP не поднимается, база не нужна (раздел 11.1, классы выделены жирным). *Источник:* задание.

**FR-38. Покрытие сверх минимума.** Случаи, которых нет в стартовых данных или которые дороги для ручной проверки (раздел 11.1). *Источник:* наше решение.

### 3.10. Артефакт

**FR-39. Спецификация.** Решение написано с ИИ-ассистентом, артефакт это папка `specs/` с `requirements.md` и `design.md`. `AI-PLAN.md` нет. Первый коммит `specs/` стоит раньше коммитов с бизнес-логикой. Если решение менялось, спецификация обновлена. *Источник:* задание (один артефакт на выбор, спецификация обновлена), наше решение (выбрана `specs/`).

## 4. Нефункциональные требования

**NFR-1. Стек.** Java 17+, Spring Boot 3, PostgreSQL 15+, Liquibase, Maven. Точные версии и доступ к данным: раздел 1. *Источник:* задание, наше решение (точные версии, `JdbcTemplate`).

**NFR-2. Сборка внутри Docker.** Для запуска и тестов нужны только Docker 23 или новее с плагинами Buildx и Compose v2 или новее (сборка использует BuildKit) и доступ к Docker Hub и Maven Central. JDK и Maven на машине не нужны. Падение теста не ломает `docker compose up` (раздел 9.2). *Источник:* наше решение.

**NFR-3. Настройка через переменные окружения.** `.env.example` перечисляет переменные из раздела 10. Файл `.env` в репозиторий не входит, настоящих секретов нет. Порт базы публикуется только на `127.0.0.1`. *Источник:* задание (переменные окружения, `.env.example`), наше решение (значения по умолчанию, порт базы).

**NFR-4. Разделение слоёв.** Контроллеры отделены от сервисного слоя и доступа к данным, логика правил и расчётов не зависит от них. Пакеты и зависимости: раздел 10. *Источник:* задание, наше решение (размещение классов).

**NFR-5. Валидация и статусы.** Параметры проверяет один класс `RequestParser`, кроме испорченной строки запроса: её проверяет `KkdController` (раздел 8.1). Некорректные параметры дают 422, а не 400. Bean Validation не используется (раздел 8). *Источник:* задание (корректные статусы, валидация), наше решение (способ).

**NFR-6. Точность.** Веса и метрики считаются в `BigDecimal`, сравнение через `compareTo`, `double` и `float` в `ru.kkd.domain` нет. *Источник:* наше решение.

**NFR-7. Независимость от часов.** `LocalDate.now()` в `src/main` нет, дата берётся из снимка прогона. Метки времени не хранятся. *Источник:* наше решение.

**NFR-8. README.** *Источник:* задание: как запустить проект, как запустить тесты, как проверить накат → откат → повторный накат. Архитектура: где живёт логика правил, как считаются метрики и дельта между прогонами. Что решение написано с ИИ-ассистентом, и ссылка на `specs/`. *Источник:* наше решение: что нужно для запуска и на чём проверялось. Таблица кодов подразделений и прогонов. Раздел «Контрольные числа стартовых данных». Строка, что `docker compose down -v` это сброс, а не откат. Смысл `resolved`. Причина выбора Spring Boot 3.5.16. Решения там, где задание молчит, и известные ограничения. Проверка третьим прогоном после цепочки.

**NFR-9. Окончания строк.** Все файлы в репозитории с окончаниями LF (раздел 1). *Источник:* наше решение.

**NFR-10. Сквозная проверка.** `scripts/check-chain.sh` поднимает проект с нуля и проверяет настоящий запуск тем же путём, каким идёт проверяющий: все числа README, стартовые данные раздела 3, контракт, ошибки, цепочку миграций, откат при открытой транзакции, третий прогон, неизменность прошлого, граничные случаи, выполняющийся прогон, другие откаты и повторный запуск с тем же томом (раздел 11.2). Скрипт сбрасывает базу проекта в начале и при успехе, все его ожидания идут с пределом времени. При первом расхождении он завершается с кодом не 0 и оставляет базу для разбора. *Источник:* наше решение.

## 5. Критерии приёмки

Команды для Git Bash и Linux, в Windows PowerShell 5.1 нужен `curl.exe`, а `diff` там нет. Ниже `$B` это `http://127.0.0.1:8080` или адрес с портом из `APP_PORT`, а `psql` это `docker compose exec -T db psql -U kkd -d kkd`. Перед запросами к API дождаться статуса `completed` у `RUN-002` в `/api/runs`. Контрольные числа: раздел README [«Контрольные числа стартовых данных»](../README.md#контрольные-числа-стартовых-данных).

AC-1...AC-11 выполняются на исходных данных. AC-12...AC-15 меняют данные: выполнять по порядку, затем сбросить базу командами `docker compose down -v` и `docker compose up -d`.

**AC-1. Запуск с нуля.** В чистой копии репозитория без `.env`:

```bash
docker compose down -v
docker compose up --build
```

Ожидается: `migrate` завершается с кодом 0, затем стартует `app`, оба прогона в `/api/runs` становятся `completed`. *Закрывает:* FR-5, FR-16, NFR-2, NFR-3.

**AC-2. Схема и стартовые данные.**

```bash
psql -c "\dt"
psql -c "select code, severity, enabled from kkd_rule order by code"
```
