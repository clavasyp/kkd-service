# Дизайн модуля ККД

Модель данных, API и ключевые решения сервиса контроля качества данных (ККД) по целям сотрудников и их ключевым результатам (КР). Что делает решение и критерии приёмки: [requirements.md](requirements.md).

Контрольные числа стартовых данных хранятся в одном месте: [README, раздел «Контрольные числа стартовых данных»](../README.md#контрольные-числа-стартовых-данных). Числа в примерах ответов API показывают форму ответа и со стартовыми данными не связаны.

Метки источника: **задание** (прямо написано в задании Backend, при расхождении главнее всего остального), **mock** (так сделано в mock API из задания Frontend, это подсказка, а не требование), **наше решение** (задание молчит, выбрали сами, причина в разделе 12).

## 1. Обзор

Сервис на Java проверяет цели и КР по 4 правилам, хранит результаты в PostgreSQL и отдаёт их тремя GET-методами. Прогон замораживает данные, правила ищут проблемы, проблемы записываются в базу, а API сравнивает два прогона. Время попадает в расчёт только через дату снимка, поэтому цель, которую никто не трогал, может получить новую проблему: факт её КР постарел.

**Стек и окружение.** Java 17. Spring Boot 3.5.16, родитель в `pom.xml`, `spring-boot-maven-plugin` объявлен. Доступ к данным через `JdbcTemplate` и `NamedParameterJdbcTemplate`, без JPA. База `postgres:17.11`, том в `/var/lib/postgresql/data`, на PostgreSQL 15.19 проверено отдельно (раздел 9.5). Миграции `liquibase/liquibase:4.31.1`. Maven только внутри образа, `Dockerfile` с целями `build`, `test`, `migrate`, `runtime`, `mvnw` нет. Порт API `${APP_PORT:-8080}`, порт базы `127.0.0.1:${DB_PORT:-15432}:5432`. Окончания строк LF: `.gitattributes` с `* text=auto eol=lf`, `.editorconfig` с `end_of_line = lf`. Источники и причины: раздел 12.

### 2.2. Таблицы результатов

Справочник правил, прогон и найденная проблема (задание). PK `kkd_issue` равен `(run_id, rule_code, object_id)`. Колонки с числом проблем нет: оно считается из строк. У `kkd_run.id`, `kkd_issue.rule_code` и `kkd_issue.object_id` задан `COLLATE "C"`, чтобы `ORDER BY` упорядочивал идентификаторы так же, как Java в `RuleEngine` и `BaseRunSelector`. Java сравнивает их по байтам UTF-8, как `COLLATE "C"` в базе UTF8, а не через `String.compareTo`: тот сравнивает единицы UTF-16 и расходится с базой на символах вне BMP, например `U+1F600` против `U+FF21`.

### 2.3. Таблицы снимков

`goal` и `key_result` хранят текущее состояние. Состояние на дату прогона лежит в снимках с ключом «прогон + объект». Снимается всё, включая закрытые цели. Знаменатели и прошлые метрики считаются из снимка и отдельно не хранятся. FK на текущие `goal`, `key_result` и `unit` нет, поэтому в снимке возможна ссылка на родителя, которого нет, и правило её поймает.

**`goal_snapshot`.** PK `(run_id, goal_id)`, `run_id` это FK на `kkd_run`. Остальные колонки: `title`, `unit_id`, `level`, `owner_name`, `parent_goal_id`, `status`, `due_date`. Типы и допустимость `NULL` как в `goal`, CHECK нет.

**`key_result_snapshot`.** PK `(run_id, kr_id)`, FK `(run_id, goal_id)` на `goal_snapshot`. Остальные колонки: `goal_id`, `title`, `measure_unit`, `target_value`, `fact_value`, `weight`, `fact_updated_on`. Типы и допустимость `NULL` как в `key_result`.

## 3. Стартовые данные

Даты в таблице целей относятся к 2026 году. Названия, ответственные, сроки, единицы, целевые и фактические значения придуманы, имена условные, совпадения с реальными людьми случайны. Символа `;` в текстах нет: Liquibase делит SQL по нему. Как данные попадают в базу: раздел 9. Что должно получиться на этих данных: [контрольные числа в README](../README.md#контрольные-числа-стартовых-данных).

Состав: в `goal` 25 строк (4 в `HQ-CIB`, 10 в `CIB-NORTH`, 11 в `CIB-SOUTH`), в `key_result` 33 строки. В снимке `RUN-001` 23 цели и 29 КР, в снимке `RUN-002` 25 целей и 33 КР. Ровно 2 прогона и 3 подразделения: упавшего прогона и подразделения без целей в данных нет, эти случаи закрыты тестами. Переноса цели между подразделениями тоже нет намеренно: у дочернего подразделения перестало бы сходиться `persisting + resolved`, и законный эффект выглядел бы как ошибка. Перенос покрыт тестом.

## 4. Правила

Реализованы `GOAL_NO_KR`, `KR_WEIGHTS_SUM`, `CASCADE_NO_PARENT`, `KR_STALE_PROGRESS`.

- **Активная цель:** ровно `status = 'active'`, срок не важен (mock, наше решение). Определение активности стоит в одном месте: `GoalRow.isActive()`. `RuleEngine` передаёт правилам только активные цели (задание: «только к активным целям и их КР»), `MetricCalculator` считает по ним знаменатели `A` и `N`. Родитель ищется среди всех целей снимка, в том числе закрытых.
- **Уровни:** `department` выше `unit`, `unit` выше `employee`. Верхний уровень `department`, его родитель не проверяется (наше решение, в задании такого исключения нет).
- **Важность** берётся из `kkd_rule` через `RuleCatalog`. Правило с `enabled = false` не срабатывает. Проблема КР относится к подразделению своей цели.

| Правило | Важность (задание) | Объект | Срабатывает | Не срабатывает |
|---|---|---|---|---|
| `GOAL_NO_KR` | critical | цель | В снимке нет ни одного КР этой цели | Есть хотя бы один КР |
| `KR_WEIGHTS_SUM` | major | цель, одна проблема на цель (mock) | КР есть, и либо сумма не равна 100 ровно, либо хотя бы один вес пуст. Сравнение `BigDecimal.compareTo`, допуска нет. Срабатывает на 99.99, 100.01, 33.33 × 3, 33.3 × 3, одном КР с весом 50, на 100 + пусто | 100, 100.00, 33.4 + 33.3 + 33.3, 23.7 + 69.4 + 6.9. Цель без КР: там только `GOAL_NO_KR` (mock). Вес 0 и отрицательный считаются как обычные числа |
| `CASCADE_NO_PARENT` | major | цель | Уровень не `department`, и выполнено одно из условий: `parent_goal_id` пуст, родителя нет в снимке, уровень родителя не строго выше | Уровень `department`, его родитель не проверяется вообще. Закрытый родитель: связь есть (mock). Родитель из другой ветки подразделений. Прыжок через уровень вверх |
| `KR_STALE_PROGRESS` | minor | КР | `DAYS.between(fact_updated_on, snapshot_date) > 45`. 46 нарушает | Ровно 45 (задание: «более»). Пустая дата. Дата в будущем. Текущая дата не участвует никогда |

**Текст `details`** — это текст для человека на русском, постоянный для одних и тех же данных, поэтому ответы до и после отката совпадают. У `KR_WEIGHTS_SUM` в нём сумма весов, у `KR_STALE_PROGRESS` число дней, у `CASCADE_NO_PARENT` причина: родитель не указан, не найден или не выше. Образец: раздел 8.4.

**Цикл целей.** Отдельной проверки нет. Цикл среди целей не верхнего уровня правило поймает: хотя бы у одной цели в цикле родитель не выше. Цикл через цель уровня `department` правило не увидит: раздел 14.

## 5. Метрики

Метрики считаются при запросе из снимков и проблем обоих прогонов и в базе не хранятся. Всё считается по **ветке**: подразделение и все его потомки на любую глубину, общим числителем и знаменателем, свои цели родителя входят, среднего долей нет (задание: «с учётом дочерних», способ из mock). Цикл в дереве подразделений не приводит к зависанию. Цели берутся из снимка своего прогона.

Обозначения: `A` активные цели ветки, `P` разные `goal_id` среди проблем ветки, `N` активные цели ветки не уровня `department`, `C` проблемы `CASCADE_NO_PARENT` в ветке.

| `key` | `title` | `unit` | Формула | `higher_is_better` | `value` равен `null`, когда |
|---|---|---|---|---|---|
| `clean_goals_share` | Доля корректных целей | `%` | `(A − P) × 100 ÷ A`. Проблема КР делает цель некорректной, цель с тремя проблемами считается один раз | `true` | `A = 0` |
| `issues_total` | Найдено проблем | `шт.` | Число строк проблем ветки | `false` | никогда, при нуле значение 0 |
| `cascade_coverage` | Покрытие каскадом | `%` | `(N − C) × 100 ÷ N` | `true` | `N = 0` |

- **Округление.** `BigDecimal`, `RoundingMode.HALF_UP`, 1 знак: 1 из 16 даёт 6.3, 2 из 3 даёт 66.7. Это отличие от mock, где округление к чётному дало бы 6.2. Доли и их дельта выводятся с одним знаком после точки, счётчик и его дельта без дробной части.
- **Дельта.** `delta = value − previous` из уже округлённых значений: 56.5 − 62.7 = −6.2.
- **`trend`.** `null`, если `value` или `previous` равен `null`. Иначе `same`, если `delta` равна 0. Иначе `better` при изменении в лучшую сторону с учётом направления метрики, в остальных случаях `worse`.
- **Разбивка.** Строк `issues_by_severity` всегда три, в порядке `critical`, `major`, `minor`, `delta = current − previous`. Если база сравнения есть, а проблем этой важности не было, `previous` равен 0.

**Особые случаи.** Статус ответа 200: подразделение существует, просто считать нечего.

| Случай | `compared_to` | Доли | `issues_total` | `issues_by_severity` | `delta` |
|---|---|---|---|---|---|
| Первый прогон или все прошлые упали | `null` | `previous`, `delta`, `trend` равны `null` | `previous`, `delta`, `trend` равны `null` | `previous` и `delta` равны `null` | Три `null` |
| В прошлом прогоне в ветке не было активных целей | есть | `previous`, `delta`, `trend` равны `null` | `previous` 0, дельта считается | `previous` 0 | Числа |
| Сейчас в ветке нет активных целей | есть | `value`, `delta`, `trend` равны `null` | `value` 0 | `current` 0 | Числа |

У `previous: null` два смысла: сравнения нет или считать было не из чего. Различаются по `compared_to`. Список проблем для ветки без целей отвечает 200 с пустым `items` и `total: 0`. Неуспешный и выполняющийся прогон сводки не дают: раздел 8.5.

## 6. Прогоны

### 6.1. Жизненный цикл и запуск

Появление строки `running` и есть запуск прогона: из стартовых данных или вставкой SQL, метода API для запуска нет. `completed` и `failed` конечны: `completed` не пересчитывается даже после перезапуска сервиса, у `failed` повторов нет. GET-методы ничего не пишут и прогоны не считают.

Новый прогон: `INSERT INTO kkd_run (id, snapshot_date) VALUES ('RUN-003', '2026-11-02')`. После ближайшего такта `RUN-003` становится `completed` и сравнивается с `RUN-002`. На стартовых данных единственное отличие — это новая проблема `KR_STALE_PROGRESS` у `KR-03-1`: её факт стал старше порога, хотя данные никто не менял. Числа: [таблица третьего прогона в README](../README.md#проверка-третьим-прогоном). Откат удаляет прогоны, добавленные руками, поэтому эту проверку выполняют после цепочки миграций. Если `RUN-003` уже вставлен, перед цепочкой нужен сброс: `docker compose down -v` и `docker compose up -d`.

### 6.2. Обработчик

`RunPoller` работает в одном потоке с паузой `KKD_RUN_POLL_MS` миллисекунд (по умолчанию 2000) после конца прошлого такта, первый такт идёт сразу после старта. В такте, пока есть прогоны `running`, он берёт самый ранний по `(snapshot_date, id)` и передаёт его в `RunProcessor`. Исключение, дошедшее до `RunPoller`, в том числе неготовность базы и неудачная запись `failed`, завершает такт: прогон остаётся `running` и берётся снова в следующем такте.

`RunProcessor` работает одной транзакцией при `REPEATABLE READ`:

1. Если снимка у прогона нет, копирует текущие таблицы в снимок. Если дата снимка раньше последнего завершённого прогона, снять его нельзя: текущие таблицы уже не описывают ту дату. Прогон получает `failed` отдельной транзакцией, как в разделе 6.3.
2. Загружает снимок и включённые строки справочника.
3. Вызывает `RuleEngine`.
4. Находит прогон для сравнения через `BaseRunSelector` (раздел 6.4).
5. Пишет строки `kkd_issue`, `compared_to_run_id` и `status = completed`. Запись статуса идёт с условием `status = 'running'` и должна изменить ровно одну строку, иначе транзакция отменяется (раздел 6.3).

Строка журнала об успехе `Прогон RUN-002: проблем ...` пишется после фиксации: когда она появилась, результат уже виден в API.

**Заморозка** — это два запроса `INSERT ... SELECT` из текущих таблиц в снимок. Они написаны в двух местах: в `004-seed.sql` и в `SnapshotRepository`. Оба видят одно состояние базы, поэтому правка целей и КР во время прогона попадает в снимок целиком или не попадает совсем.

### 6.3. Сбои

| Случай | Действие |
|---|---|
| Ошибка логики или данных, в том числе любая ошибка SQL, кроме случаев двух строк ниже | Транзакция отменяется. Отдельной транзакцией `status = failed`, в `error` постоянный текст |
| Таблицы нет: `SQLState` = `42P01` | `failed` не ставится, такт пропускается. Это нормальное состояние между откатом и накатом |
| Нет связи с базой или взаимная блокировка: `SQLState` = `40P01` | То же: `failed` не ставится, такт пропускается |
| Строки `running` уже нет, когда пишется `completed`: запись изменила 0 строк | Транзакция отменяется, проблемы и снимок не фиксируются. Отдельной транзакцией `failed`. Если и эта запись изменила 0 строк, исключение завершает такт: строка, которая осталась `running`, например из-за триггера, подавляющего запись, берётся снова только после паузы, а не сразу. Прогоны после неё в порядке `(snapshot_date, id)` ждут, пока запись не станет возможна |
| Сервис упал посреди прогона | Транзакция отменилась, прогон остался `running` и выполнится заново |
| JVM не хватило памяти посреди прогона, например `OutOfMemoryError` | Это `Error`, а не ошибка данных: его не ловят ни `RunProcessor`, ни `RunPoller`. Транзакция отменилась, прогон остался `running` и считается снова в следующем такте, а следующие прогоны ждут. На стартовых данных этого нет |

Вторую и третью строки различает один класс `DbState`. Им пользуются `RunPoller`, `RunProcessor` (пропустить такт или записать `failed`) и `ApiExceptionHandler` (503 или 500). Признаком отсутствия таблицы служит только `SQLState`, а не тип исключения: другая ошибка SQL, например опечатка в колонке (`42703`), идёт по первой строке. Нет связи значит: класс `08`, коды остановки сервера `57P01`, `57P02`, `57P03`, исключения получения соединения и начала транзакции, а также сбой отката после обрыва на фиксации, когда исходной ошибки нет и причина без `SQLState`. Взаимная блокировка — это временный сбой: повтор проходит. Откат с запросами её не создаёт: раздел 9.1.

**Текст в `error`** постоянный и не содержит текста исключения: отдельный для снимка, который нельзя снять, и общий для остальных случаев. Образец: раздел 8.2. Текст исключения и стек только в журнале.

### 6.4. Выбор прогона для сравнения

`BaseRunSelector` получает список прогонов и возвращает последний `completed` с меньшим `(snapshot_date, id)`. Упавшие и выполняющиеся пропускаются. Если такого нет, сравнения нет: `compared_to_run_id` остаётся пустым, и ответ выглядит как у первого прогона. API читает базу сравнения из `kkd_run.compared_to_run_id` и заново её не выбирает.

## 7. Сравнение прогонов

**Ключ** — это пара `(rule_code, object_id)` (задание: «та же самая, если совпадают правило и объект»). Текст `details` в ключ не входит.

| Счётчик | Условие | В какую ветку попадает |
|---|---|---|
| `new` | Пара есть в текущем прогоне, нет в базе сравнения | По `unit_id` текущей строки |
| `persisting` | Пара есть в обоих | По `unit_id` текущей строки |
| `resolved` | Пара есть в базе сравнения, нет в текущем | По `unit_id` прошлой строки |

- **Смысл `resolved`.** Пара пропала по любой причине, в том числе при закрытии цели. Причину модуль не различает, README говорит об этом прямо.
- **Область счёта.** Статус считается по всей организации, затем счётчик относится к подразделению по таблице выше. Разбивка `issues_by_severity`, счётчики `delta` и фильтр `unit_id` в `issues` считаются с дочерними. `new + persisting` равно текущим проблемам ветки.
- **Перенос цели в другое подразделение.** Пара та же, поэтому это `persisting` там, где объект лежит сейчас. Если пара была в N, а стала в S, то в S это `persisting`, в N она не попадает ни в один счётчик, у родителя это `persisting`. Поэтому у дочернего подразделения равенство `persisting + resolved = previous` может законно не сойтись.
- **Вернувшаяся проблема** снова `new`: сравниваем только с одним прогоном. **На первом прогоне** сравнения нет, поэтому три счётчика равны `null`, а не 0 (задание).

## 8. Контракт API

Методов ровно три. Имена полей snake_case (пример задания), поля с `null` остаются в ответе, дата пишется как `2026-10-26`, русский текст приходит без искажений. Порядок полей как в примерах ниже. Неизвестные параметры запроса игнорируются, если строка запроса разобрана без ошибок: раздел 8.1. Имена полей и параметров взяты из mock там, где задание их не называет. Контроллер принимает параметры строками и передаёт в `RequestParser`: он один решает, корректны ли значения. Испорченную строку запроса проверяет сам контроллер: раздел 8.1. Некорректные параметры дают 422, а не 400.

### 8.1. Параметры

| Параметр | Где | Обязателен | Допустимо | Ошибка |
|---|---|---|---|---|
| `run_id` | `summary`, `issues` | да | Непустая строка | Нет или пусто: 422. Неизвестный: 404 |
| `unit_id` | `summary` | да | Непустая строка | Нет или пусто: 422. Неизвестное: 404 |
| `unit_id` | `issues` | нет | Непустая строка, включает дочерние | Пусто: 422. Неизвестное: 404 |
| `rule_code` | `issues` | нет | Один из 6 кодов задания. Код выключенного правила: 200 и пустой список | Иначе 422 |
| `severity` | `issues` | нет | `critical`, `major`, `minor`, регистр важен | Иначе 422 |
| `limit` | `issues` | нет, по умолчанию 20 | Целое от 1 до 200 | `abc`, пусто, 0, −1, 201: 422, без молчаливого обрезания |
| `offset` | `issues` | нет, по умолчанию 0 | Целое от 0 до 2147483647 | `abc`, пусто, −1, 2147483648: 422. За концом списка: 200 и пустой `items` |

- **Числа.** Только цифры ASCII: `+5`, ` 5` и цифры других алфавитов дают 422.
- **Нулевой символ** в `run_id` или `unit_id` даёт 422: база не принимает его даже в условии поиска, поэтому такого значения быть не может (наше решение).
- **Испорченная строка запроса** `summary` и `issues` даёт 422, даже если испорчен неизвестный параметр (наше решение). Это неверная запись `%XX`, например `limit=%zz` или `%zz=1`, и кусок без имени, например `=1` или `=`. Tomcat отбрасывает такой кусок и ставит признак ошибки разбора, а причину хранит только первую: в `=1&severity=%zz` фильтр `severity` молча не применился бы, поэтому `KkdController` отвергает любую ошибку разбора. Значение до `RequestParser` не доходит. Пустые куски, как в `&&`, и пустое значение, как в `foo=`, ошибкой не считаются. Неверный UTF-8, например `%FF`, Tomcat заменяет символом U+FFFD и параметр не отбрасывает, поэтому значение проверяется как обычное: `limit=%FF` даёт 422, `run_id=%FF` даёт 404, неизвестный параметр `foo=%FF` игнорируется.
- **Символы без кодирования.** Символы `"`, `<`, `>`, `[`, `\`, `]`, `^`, `` ` ``, `{`, `|`, `}` в строке запроса Tomcat по умолчанию отвергает ответом 400 с HTML. Настройка `server.tomcat.relaxed-query-chars` пропускает их к обычным проверкам (задание: некорректные параметры дают 422, формат ошибки единый). Поэтому `limit=[1]` и `severity=a|b` дают 422, `unit_id={x}` даёт 404, а неизвестный параметр `x=[1]` игнорируется. Пробел, управляющие символы и байты не ASCII без кодирования Tomcat отвергает всё равно: раздел 14.
- **Источники.** Имена `run_id`, `unit_id`, `limit`, `offset`: задание. Остальные имена, значения по умолчанию и предел 200: mock. Обязательность: наше решение, `latest` и подстановки нет.
- **Граница 404 и 422.** 404 значит: значение по форме допустимо, но такого прогона или подразделения нет, например `run_id=abc`. Остальные некорректные значения дают 422, в том числе пустой `run_id`, неизвестный `rule_code`, неверная `severity` и `limit=0`.
- **Порядок проверок.** Форма параметров (422), затем прогон (404), затем подразделение (404), затем состояние прогона (409). В ответе одна ошибка, первая найденная. Значит, `run_id=RUN-999&limit=-1` даёт 422.

### 8.5. Ошибки

Формат один для всех ошибок таблицы: `{"error": {"code": "...", "message": "..."}}` (задание). Сообщения на русском, без стека и имён классов Java. Значения `code` задание заменило многоточием, поэтому это наш выбор, коды взяты из mock там, где они есть.

| Статус | `code` | Когда | Источник |
|---|---|---|---|
| 422 | `INVALID_PARAM` | Нет обязательного параметра, пустое значение, неверный тип, вне диапазона, неизвестный код, испорченная строка запроса: неверная запись `%XX` или кусок без имени | статус: задание, код: mock |
| 404 | `RUN_NOT_FOUND` | Неизвестный прогон, включая `run_id=abc` | статус: задание, код: mock |
| 404 | `UNIT_NOT_FOUND` | Неизвестное подразделение | статус: задание, код: mock |
| 404 | `NOT_FOUND` | Неизвестный путь, с любым заголовком `Origin` | наше решение |
| 405 | `METHOD_NOT_ALLOWED` | `POST`, `PUT`, `PATCH`, `DELETE`, например `POST /api/runs`. `HEAD` и `OPTIONS` без заголовка `Origin` Spring обслуживает сам: 200 | наше решение |
| 400 | `REQUEST_NOT_SUPPORTED` | Испорченный адрес, который Tomcat пропускает: неверная запись `%XX` в части сегмента после `;`, например `/api/runs;x=%zz`. Сообщение «Адрес запроса содержит испорченное кодирование». Статус тот же, что Tomcat сам даёт на другие испорченные адреса (раздел 14), а это не параметр запроса, поэтому не 422 | наше решение |
| Клиентский статус Spring MVC, например 406 | `REQUEST_NOT_SUPPORTED` | Прочие ошибки Spring MVC с клиентским статусом: статус и заголовки сохраняются, тело в едином формате при любом `Accept`. В том числе 406 на `Accept`, из которого получается больше 50 совместимых типов, например 26 разных `application/*;q=...`: Spring не может их отсортировать, как и `Accept` длиннее 50 элементов | наше решение |
| 409 | `RUN_FAILED` | `summary` или `issues` для прогона `failed` | mock |
| 409 | `RUN_IN_PROGRESS` | `summary` или `issues` для прогона `running` | mock |
| 503 | `DB_NOT_READY` | Таблицы нет (`SQLState` = `42P01`): состояние между откатом и накатом. База недоступна или взаимная блокировка (`40P01`): временный сбой. Все соединения пула заняты дольше 3 с: раздел 14 | наше решение |
| 500 | `INTERNAL_ERROR` | Непредвиденная ошибка сервера, в том числе другие ошибки SQL | наше решение |

```json
{ "error": { "code": "INVALID_PARAM", "message": "Параметр limit должен быть целым числом от 1 до 200" } }
{ "error": { "code": "RUN_NOT_FOUND", "message": "Прогон RUN-999 не найден" } }
{ "error": { "code": "RUN_FAILED", "message": "Прогон RUN-009 завершился с ошибкой" } }
{ "error": { "code": "DB_NOT_READY", "message": "База данных не готова, повторите запрос позже" } }
```

`ApiExceptionHandler` переводит исключения в эту таблицу и выбирает статус HTTP. `KkdException` несёт только `code` и `message`.

`BrokenUriFilter` стоит перед Spring MVC и отвечает 400 на адрес, который не декодируется целиком (наше решение). Часть сегмента после `;` Tomcat не проверяет, а Spring MVC декодирует её раньше обработчика ошибок и на `%zz` отвечал бы 500 с HTML. Остальную часть адреса Tomcat проверяет сам: раздел 14. Адрес проверяется целиком, потому что параметр с пустым именем, как в `;=%zz`, Spring при разборе пути пропускает, но декодирует позже, при записи ответа.

Настройка `spring.datasource.hikari.connection-timeout=3000` (наше решение): при лежащей базе 503 приходит за секунды, а не за 30 с по умолчанию. Настройка `server.tomcat.relaxed-query-chars`: раздел 8.1. Служебный путь Spring Boot `/error` отключён (наше решение): других методов, кроме трёх, нет, поэтому он отвечает как неизвестный путь. Обработчик статических ресурсов отключён (наше решение): статических файлов нет, а он обслуживал все неизвестные пути и проверял у них `Origin`, поэтому испорченный `Origin`, например `http://a:b`, давал 403 «Invalid CORS request» текстом вместо 404. Фильтр форм и разбор `multipart` отключены (наше решение): у методов нет тела, а с этими компонентами испорченная форма на `PUT` и `multipart/form-data` без `boundary` давали бы 500. Уровни журнала `Http11Processor` и `ProxyConnection` подняты (наше решение): на испорченный HTTP-запрос и при обрыве связи они пишут стек, хотя клиент получает обычный ответ, а смену состояния базы и так пишет `RunPoller`. Уровень `PageNotFound` поднят (наше решение): Spring пишет WARN на каждый неизвестный путь и неподдерживаемый метод, а это ошибки клиента, ответ на которые уже в едином формате. Что остаётся вне единого формата: раздел 14.

## 9. Миграции

Инструмент: Liquibase 4.31.1. Отдельный контейнер `migrate` выполняет и накат при `docker compose up`, и откат, и повторный накат. Сервис миграции не запускает, `liquibase-core` в его зависимостях нет.

### 9.1. Файлы и наборы изменений

Папка `db/changelog/` в корне репозитория. Схема и данные в формате Liquibase SQL: откат виден прямо под изменением. Автор всех наборов `kkd`.

| Файл | Changeset | Что делает | Откат |
|---|---|---|---|
| `db.changelog-master.yaml` | `000-tag-empty` | `tagDatabase v0-empty`, затем `include` остальных файлов | Автоматически. Откат к этой метке убирает и её строку |
| `001-org-goals.sql` | `001-unit`, `002-goal`, `003-key-result` | Предметные таблицы | `DROP TABLE` |
| `002-kkd.sql` | `004-kkd-rule` | Справочник | `DROP TABLE` |
| | `005-kkd-rule-rows` | 6 строк справочника | `DELETE FROM kkd_rule` |
| | `006-kkd-run` | Прогон | `DROP TABLE` |
| | `007-kkd-issue` | Проблема | `LOCK TABLE kkd_run`, затем `DROP TABLE` |
| `003-snapshots.sql` | `008-goal-snapshot`, `009-kr-snapshot` | Снимки | `LOCK TABLE kkd_run`, затем `DROP TABLE` |
| `004-seed.sql` | `010-seed-history` | Один changeset по порядку: подразделения, цели и КР на 19.10, строка `RUN-001`, заморозка, изменения за неделю, строка `RUN-002`, заморозка | `DELETE` без условия из семи таблиц по порядку: `kkd_issue`, `key_result_snapshot`, `goal_snapshot`, `kkd_run`, `key_result`, `goal`, `unit` |

**Стартовые данные одним changeset:** он применяется и откатывается целиком одной транзакцией, поэтому обработчик не увидит прогон с половиной снимка, а откату не надо восстанавливать прежние значения. **`DELETE` без условия** убирает и проблемы, записанные сервисом, и прогоны, добавленные руками: иначе FK не даст удалить прогоны, а проверка на пустой базе этого не увидит.

**`LOCK TABLE kkd_run` в откате** (наше решение). Все три метода читают `kkd_run` первым, а `DROP TABLE` сначала берёт свою таблицу и только потом таблицу из FK. Без этой строки запрос, успевший прочитать `kkd_run`, и откат ждут друг друга, и PostgreSQL прерывает одного из них. Проверено запуском: `rollback` завершился с `deadlock detected` и кодом 1. С этой строкой откат дожидается конца таких запросов, а новые ждут конца шага отката.

### 9.3. Команды цепочки

Для Git Bash и Linux. В Windows PowerShell 5.1 вместо `curl` нужен `curl.exe`, а `diff` там нет.

```bash
# Порт сервиса. Compose читает .env сам, а оболочка нет: если порт менялся, сначала export APP_PORT=<тот же порт>
# Адрес 127.0.0.1, а не localhost: в Windows localhost может уйти на [::1], где порт держит другая программа, и curl зависнет
# < /dev/null у docker compose run и exec: без него Docker может забрать следующие строки вставленного блока себе как ввод, и они не выполнятся
B=http://127.0.0.1:${APP_PORT:-8080}

# Ждём, пока сервис посчитает оба прогона: 60 попыток, затем сообщение и код ошибки
wait_runs() { for i in $(seq 1 60); do curl -sf --max-time 5 "$B/api/runs" | grep -q '"id":"RUN-002","status":"completed"' && return 0; sleep 1; done; echo "не дождались RUN-002"; return 1; }

# 1. Накат вместе со всем проектом. Сохраняем ответы до отката
docker compose up -d --build
wait_runs
curl -s "$B/api/runs" > before.json
curl -s "$B/api/kkd/summary?run_id=RUN-002&unit_id=HQ-CIB" > before-summary.json
curl -s "$B/api/kkd/issues?run_id=RUN-002&limit=200" > before-issues.json

# 2. Откат всего: схема и данные
docker compose run --rm migrate rollback --tag=v0-empty < /dev/null
docker compose exec -T db psql -U kkd -d kkd -c "\dt" < /dev/null     # только databasechangelog и databasechangeloglock
docker compose exec -T db psql -U kkd -d kkd -c "select count(*) from databasechangelog" < /dev/null     # 0: откат убрал и строку метки
curl -si "$B/api/runs"     # HTTP 503 и {"error":{"code":"DB_NOT_READY",...}}

# 3. Повторный накат. Сервис перезапускать не нужно. Каждый diff ничего не печатает: ответы те же
docker compose run --rm migrate update < /dev/null
wait_runs
curl -s "$B/api/runs" | diff before.json -
curl -s "$B/api/kkd/summary?run_id=RUN-002&unit_id=HQ-CIB" | diff before-summary.json -
curl -s "$B/api/kkd/issues?run_id=RUN-002&limit=200" | diff before-issues.json -
```

`psql -U kkd -d kkd` рассчитан на значения по умолчанию. Повторный `rollback --tag=v0-empty` без наката завершается ошибкой `Could not find tag` с кодом 1: откатывать уже нечего, а метка ушла вместе с остальным. Сначала нужен `update`. После правки файлов в `db/changelog` нужна пересборка: `docker compose build migrate`.

**Другие команды.**

| Команда | Что делает |
|---|---|
| `docker compose run --rm migrate rollback-count --count=1` | Откат только стартовых данных. Таблицы остаются, `/api/runs` даёт пустой список, сводка 404 |
| `docker compose down -v`, затем `docker compose run --rm migrate update-testing-rollback` | Разовая проверка всех откатов на пустой базе. Строк, записанных сервисом, она не видит, поэтому дополняет цепочку, а не заменяет её |
| `docker compose down -v` | **Сброс базы, это не откат** |
| `docker compose run --rm migrate release-locks` | Снять блокировку Liquibase, если контейнер прервали посреди работы |

### 9.4. Что происходит с данными

Сервис во время цепочки не падает и не требует перезапуска.

- **После `up`:** 8 рабочих и 2 служебные таблицы, стартовые данные и снимки, `kkd_issue` посчитана сервисом, `GET /api/runs` даёт 200 и два `completed`.
- **После отката:** только 2 служебные таблицы, `databasechangelog` пуст, `update` создаёт метку заново. Любой из трёх методов на запрос с корректной формой отвечает 503 `DB_NOT_READY`.
- **Посреди отката и наката** ненадолго возможны 200 с пустым списком у `/api/runs` и 404 `RUN_NOT_FOUND` у сводки и списка проблем: таблицы есть, а строк нет. Сами запросы откату не мешают: раздел 9.1.
- **Сразу после наката:** строки те же, `kkd_issue` пуста. Не дольше такта прогоны видны как `running`, а сводка и список проблем отвечают 409 `RUN_IN_PROGRESS`.
- **После такта:** те же строки проблем с теми же `id`. Ответы всех трёх методов совпадают побайтно с ответами до отката: снимок тот же, возраст считается от `snapshot_date`, а текущая дата в расчёте не участвует.
- **Повторный `up` с томом на месте** после наката ничего не применяет. После отката `up` снова запускает `migrate`, и он накатывает всё: это тот же повторный накат. **`docker compose restart app`** ничего не меняет: `completed` не пересчитываются.

### 9.5. Установка на отдельный стенд

Задание называет цепочку миграций условием приёмки проекта на общем тестовом стенде. Поэтому образы к compose не привязаны: стадии `migrate` и `runtime` собираются отдельно, а подключение к базе получают только из переменных окружения: `LIQUIBASE_COMMAND_URL`, `LIQUIBASE_COMMAND_USERNAME`, `LIQUIBASE_COMMAND_PASSWORD`, `LIQUIBASE_COMMAND_CHANGELOG_FILE` у `migrate` и `DB_URL`, `DB_USER`, `DB_PASSWORD` у сервиса. Команды: README, раздел «Установка на отдельный стенд».

- **Права.** Хватает пользователя — владельца базы без прав суперпользователя. Миграции создают таблицы в схеме `public`, расширений и ролей не создают.
- **Стартовые данные** входят в миграции (`004-seed.sql`) и попадают на стенд вместе со схемой. Задание требует, чтобы `docker compose up` поднимал и данные, поэтому отдельного контекста Liquibase для них нет.
- **Порядок** тот же, что в compose: сначала `update`, потом сервис. Перед откатом ждать `completed` у обоих прогонов. Данные на каждом шаге: раздел 9.4.
- **Проверено запуском** на PostgreSQL 15.19, базой владел пользователь без прав суперпользователя. Накат, откат с ответом 503 и повторный накат прошли, ответы трёх методов до отката и после наката совпали побайтно и совпали с ответами compose на `postgres:17.11`. Полная сквозная проверка на копии проекта, где у `db` образ `postgres:15`, тоже прошла, кроме двух проверок `git`: копия не репозиторий.

### 11.2. Сквозная проверка: `scripts/check-chain.sh`

Запуск: `bash scripts/check-chain.sh`, бит исполнения не нужен, текущая папка не важна. Это `bash`, `curl`, `docker` и обычные утилиты, не JUnit, в запуск тестов не входит. Адрес сервиса скрипт берёт у `docker compose port`, `psql` запускает через `docker compose exec`, такт задаёт сам: `KKD_RUN_POLL_MS=2000`. Поэтому он работает со своими портами и базой в `.env` и с `COMPOSE_PROJECT_NAME`.

**Контрольных чисел в скрипте нет.** При запуске он разбирает таблицы README и сверяет все их строки простым поиском строки в ответе, при расхождении главнее README. Названий подразделений, дат прогонов и базы сравнения в скрипте тоже нет: он берёт их из таблиц README раздела «Подразделения и прогоны» и сверяет с базой и ответами API. Если таблицы нет, в ней нет строк, другое число колонок, строк или неверный вид значения, скрипт сообщает, что формат README изменился. Таблицы разделов 3.2, 3.3 и 3.4 он так же разбирает при запуске: это карта проблем и значения снимков, поэтому правка формата этих таблиц даёт расхождение.

**Поведение.** Все ожидания и команды идут с пределом времени и кодом ошибки, поэтому скрипт не зависает. Настройки окружения его не меняют: `CDPATH`, `COMPOSE_FILE`, `GREP_OPTIONS` снимаются, `DOCKER_BUILDKIT=1` и `LC_ALL=C.UTF-8` задаются, `curl` идёт без прокси и `~/.curlrc`. В Git Bash команду по пределу снимает `taskkill`: сигнал не доходит до `docker.exe`. При первом расхождении он печатает, что проверялось, ожидание, факт, хвост журнала команд этого шага и подсказки, завершается с кодом не 0, а база и временная папка остаются для разбора. При успехе он выполняет `docker compose down -v`, удаляет временную папку и печатает число проверок и время.

### 11.3. CI

`.github/workflows/ci.yml` на каждый `push` выполняет на `ubuntu-24.04` команду `docker build --target test --progress=plain .` и `bash scripts/check-chain.sh`, предел 30 минут, при сбое печатает `docker compose ps -a` и `docker compose logs`. Это наше решение, задание CI не требует. Зачем: автор работает на Windows, а CI показывает, что тесты и сквозная проверка проходят на чистой машине с Linux.

В стартовых данных переносов нет | В определении задания подразделения нет. Сравнение внутри ветки сделало бы перенесённую проблему новой. Прошлое не меняется задним числом | задание, наше решение |

## 13. Что сознательно не делаем

| Что | Почему |
|---|---|
| Страница ККД и любой фронтенд | Задание просит сервис и REST API для страницы |
| Авторизация и роли | Задание их не требует. Все методы открыты |
| `POST /api/runs`, расписание | В задании только GET, еженедельный запуск оно называет планом. Прогон запускается вставкой строки |
| `GET /api/meta`, `GET /api/kkd/units` | Нет в задании. Коды подразделений в README |
| Правила `GOAL_NO_OWNER` и `KR_NO_TARGET` | Задание просит любые 4 из шести. Коды есть в справочнике, но правила не считаются и в метрики не входят |
| `delta_status` в строке проблемы, список исправленных | Нет в задании. Та же проблема видна по одинаковому `id` в разных прогонах, исправленные только счётчиком |
| `limit` и `offset` у `/api/runs` | Задание просит пагинацию только у `issues` |
| `finished_at`, метки времени | Не нужны логике и API. Текущее время мешало бы сравнению ответов до и после отката |
| Суррогатный `id` проблемы | Ключ `(run_id, rule_code, object_id)` равен определению задания и не меняется после отката |
| Снимок дерева подразделений | В задании дерево не меняется. Ограничение записано в разделе 14 |
| Таблица сотрудников | Нет в перечне, правилам не нужна |
| Bean Validation (`@Min`, `@Valid`, `@Validated`) | Параметры разбирает один класс, поэтому Spring не выдаст 400 или 500 |
| JPA, Lombok, Actuator, OpenAPI, `mvnw` | Лишний код на проверку, пользы для задания нет |
| Несколько значений в фильтре, поиск, сортировка | Нет в задании |
| Оформление отклика: ссылка в резюме, срок сдачи, ответы о мотивации, доступ к репозиторию | Это не поведение решения |

## 14. Известные ограничения

| Ограничение | Что это значит |
|---|---|
| Дерево подразделений одно на все прогоны | Перенос цели учтён: `unit_id` лежит в снимке. Реорганизация самого дерева не учтена: прошлые значения родителя пересчитаются по новому дереву |
| Цикл целей через уровень `department` не виден | Сама цель верхнего уровня не проверяется, а у её дочерней цели родитель выше. Тест `CascadeNoParentRuleTest` фиксирует это поведение |
| Заморозка написана в двух местах | SQL в `004-seed.sql` и в `SnapshotRepository` может разойтись. Скрипт сверяет снимок нового прогона с текущими таблицами по числу строк и значениям, а снимки стартовых прогонов с разделом 3 |
| SQL репозиториев без JUnit | `docker build --target test` его не видит: ошибку в запросе, порядке выдачи или `goal_title` покажет только `scripts/check-chain.sh` |
| Ошибки до Spring MVC не в едином формате | На испорченный адрес, например `/api/%2F`, `/api/%zz` или `/api/[x]`, на строку запроса с пробелом, управляющим символом или байтами не ASCII без кодирования `%XX` и на запрос длиннее 8 КБ Tomcat сам отвечает 400 с HTML, на метод `TRACE` 405 с HTML. До кода сервиса такие запросы не доходят. Исключение: параметр пути после `;` Tomcat не проверяет, его испорченную запись отклоняет фильтр сервиса, 400 в едином формате (раздел 8.5) |
| CORS не настроен | Предварительный запрос `OPTIONS` с `Origin` и `Access-Control-Request-Method` к одному из трёх путей получает от Spring 403 «Invalid CORS request» текстом вне единого формата. К неизвестному пути такой запрос, как и любой другой, получает 404 в едином формате. В задании CORS нет |
| Все соединения пула заняты дольше 3 с | Запрос получает 503 `DB_NOT_READY`, хотя база работает: 10 соединений Hikari по умолчанию и `connection-timeout=3000`. Проверено запуском: при заблокированной `kkd_run` из 14 одновременных `GET /api/runs` 9 дождались 200, 5 получили 503 через 3.0 с. Ответ верен по смыслу, временный сбой и «повторите запрос позже», но текст говорит о готовности базы |
| Повтор параметра | Значения склеиваются через запятую: `run_id=A&run_id=B` даёт 404 с `A,B` в сообщении, а `limit`, `severity`, `rule_code` дают 422. Нескольких значений в фильтре нет, раздел 13 |
| `NaN` в числах КР | `NUMERIC` хранит `NaN`, а `BigDecimal` его не читает: прогон получает `failed` по первой строке раздела 6.3, и так каждый следующий, пока значение не исправят. В стартовых данных таких значений нет |
| Стек от Spring при обрыве связи | Запрос, у которого связь оборвалась посреди транзакции, получает 503, но `TransactionInterceptor` сам пишет ERROR со стеком. Настройка уровня не отключена: иначе пропал бы и стек настоящей ошибки при сбое отката |
| Опечатка в имени таблицы выглядит как отсутствие таблицы | Она тоже даёт `42P01`: прогон остаётся `running`, API отвечает 503. Её выдаст цикл ожидания с пределом |
| При обычном такте выполняющийся прогон виден только в окне такта | Скрипт видит его через медленный такт, шаг 8 раздела 11.2: `KKD_RUN_POLL_MS=600000 docker compose up -d app`, затем вставка строки с новой датой. Так же можно посмотреть вживую. Прогон останется в базе, поэтому перед цепочкой нужен сброс |
| Равенство `persisting + resolved = previous` у дочернего подразделения | При переносе цели может законно не сойтись, у родителя сходится |
| Сравнение только с одним прогоном | Вернувшаяся проблема снова `new`, истории статусов нет |
| Прогоны, добавленные руками, не переживают откат | Откат их удаляет, повторный накат возвращает только `RUN-001` и `RUN-002` |
| Откат сразу после наката | Обработчик в этот момент пишет проблемы, и `DELETE` может столкнуться с ними. Команды ждут `completed` |
| Прогон с датой раньше последнего завершённого и без снимка | Получает `failed`: текущие таблицы не описывают ту дату |
| Правка строки `kkd_run` посреди её расчёта | При `REPEATABLE READ` запись `completed` получает ошибку `40001`, и прогон становится `failed`. Сам сервис так не делает, это возможно только при ручной правке |
| `failed` не повторяется | Для повтора нужна новая строка прогона с новым идентификатором |
| Запуск прогонов только вставкой SQL | Еженедельного расписания нет: задание называет его планом |
| Changelog лежит в образе `migrate` | После правки файлов нужна пересборка |
| Кириллица в имени самой папки проекта | `docker compose up --build` падает с `failed to dial gRPC`: значение из имени папки идёт в заголовок gRPC, а там допустим только ASCII. Если в имени только кириллица, `docker compose` без `COMPOSE_PROJECT_NAME` падает раньше: `project name must not be empty`. `docker build` такая папка не мешает, родительские папки могут быть любыми. Скрипт сообщает об этом на шаге 0 |
