# Модуль контроля качества данных по целям (ККД)

Сервис на Java проверяет цели сотрудников и ключевые результаты (КР) по 4 правилам, хранит результаты в PostgreSQL и отдаёт их через REST API тремя GET-методами. Страницы в этом репозитории нет: API рассчитан на её разработчика, все значения приходят готовыми.

| Где | Что лежит |
|---|---|
| `src/main/java/ru/kkd` | Код сервиса. Логика правил: `domain/rules` |
| `src/test/java/ru/kkd` | Тесты JUnit 5 |
| `db/changelog` | Миграции Liquibase и стартовые данные |
| `scripts/check-chain.sh` | Сквозная проверка настоящего запуска |
| [`specs/`](specs/) | Спецификация: требования и дизайн |
| `.env.example` | Образец настроек. Файл `.env` не обязателен |

## Что нужно

- Docker 23 или новее с плагинами Buildx и Compose v2 или новее: сборка использует BuildKit. Проверка: `docker buildx version` и `docker compose version`. В Docker Desktop оба плагина есть. В Ubuntu с пакетом `docker.io` плагин Buildx ставится отдельно: `sudo apt install docker-buildx`.
- Доступ к Docker Hub и Maven Central при первой сборке.
- Свободные порты 8080 и 15432. Другие порты можно задать в `.env`, образец в `.env.example`.
- Имя самой папки проекта без кириллицы, иначе `docker compose` не соберёт проект. Родительские папки могут быть любыми.

JDK и Maven для запуска не нужны: сборка идёт внутри Docker.

Для проверок ниже нужны ещё `bash`, `curl` и `diff`. В Windows они есть в Git Bash.

На чём проверялось:

- Windows 11, Docker 29.2, Compose 5.0: машина автора.
- Ubuntu 24.04 в GitHub Actions: тесты и сквозная проверка, запуск CI зелёный.
- Docker 23.0.0, Compose 2.16.0: вложенный демон на машине автора, сборка без сети с заранее заполненным кэшем. Тесты и сквозная проверка прошли.
- PostgreSQL 15.19 вместо 17.11: команды раздела [«Установка на отдельный стенд»](#установка-на-отдельный-стенд) и сквозная проверка на копии проекта с этим образом базы.

Сколько идёт первая сборка. Замер в CI на чистой машине: `docker build --target test` занял 44 с, после него `docker compose up -d --build` занял 37 с, при этом стадия `build` уже лежала в кэше. Прямого замера `docker compose up --build` с совсем пустым кэшем нет. Оценка, а не замер: около минуты-полутора на чистой машине. Время зависит от сети.

## Запуск

```bash
docker compose up --build
```

Поднимаются база, миграции со стартовыми данными и сервис. Файл `.env` не обязателен: без него работают те же значения по умолчанию. Хватает и обычного `docker compose up`: при первом запуске образы соберутся сами, а `--build` пересобирает их после правок кода.

При первом запуске сервис готов, когда в журнале появилась строка `Прогон RUN-002: проблем ...`. При повторном запуске на том же томе прогоны уже посчитаны и такой строки нет: сервис готов, когда отвечает проверка ниже. Строка `ERROR:  relation "public.databasechangeloglock" does not exist` от `db` при первом запуске — это не сбой: в пустой базе ещё нет служебной таблицы Liquibase.

Предупреждение `Docker Compose requires buildx plugin to be installed` и ошибка `the --mount option requires BuildKit` значат, что нет плагина Buildx: раздел [«Что нужно»](#что-нужно).

Проверить сервис можно из другого терминала:

```bash
curl http://127.0.0.1:8080/api/runs
```

В Windows PowerShell 5.1 вместо `curl` нужен `curl.exe`.

В ответе оба прогона со статусом `completed`, сверху `RUN-002`, и он сравнивается с `RUN-001`. Значения `totals.issues_total` равны числу проблем `HQ-CIB` в разделе [«Контрольные числа стартовых данных»](#контрольные-числа-стартовых-данных).

## Тесты

```bash
docker build --target test --progress=plain .
```

Тесты идут внутри сборки образа, база и HTTP не нужны. Обязательные сценарии задания: `KrStaleProgressRuleTest` и `KrWeightsSumRuleTest` (два правила на граничных данных), `MetricCalculatorTest` (расчёт метрики), `DeltaCalculatorTest` (расчёт дельты).

Строки `ERROR` в выводе пишут тесты сбоев: они нарочно вызывают ошибки. Итог виден в строках `Tests run: ..., Failures: 0` и `BUILD SUCCESS`.

Ошибка `unknown flag: --progress` или `Install the buildx component` значит, что нет плагина Buildx: раздел [«Что нужно»](#что-нужно).

Повторный запуск без изменений кода берётся из кэша: в выводе `CACHED`, строк `Tests run` нет. Запустить тесты заново в Git Bash или Linux:

```bash
docker build --target test --progress=plain --build-arg RERUN=$(date +%s) .
```

Флаг `--no-cache-filter test` тоже запускает тесты, но сбрасывает кэш Maven, и зависимости скачиваются заново.

## Накат → откат → повторный накат

Миграции выполняет отдельный контейнер `migrate` с Liquibase. Сервис сам миграции не запускает и не накатывает изменения обратно при перезапуске. Но сразу после старта он считает прогоны, и откат в этот момент может столкнуться с его записью, поэтому перед откатом команды ждут статуса `completed`.

Команды для Git Bash и Linux, сервис при этом продолжает работать:

```bash
# Порт сервиса. Compose читает .env сам, а оболочка нет: если порт менялся, сначала export APP_PORT=<тот же порт>
# Адрес 127.0.0.1, а не localhost: в Windows localhost может уйти на [::1], где порт держит другая программа, и curl зависнет
# < /dev/null у docker compose run и exec: без него Docker может забрать следующие строки вставленного блока себе как ввод, и они не выполнятся
B=http://127.0.0.1:${APP_PORT:-8080}

# Ждём, пока сервис посчитает оба прогона: 60 попыток, затем сообщение и код ошибки
wait_runs() { for i in $(seq 1 60); do curl -sf --max-time 5 "$B/api/runs" | grep -q '"id":"RUN-002","status":"completed"' && return 0; sleep 1; done; echo "не дождались RUN-002"; return 1; }

# 1. Накат вместе со всем проектом. Сохраняем ответы до отката
docker compose up -d --build
wait_runs
curl -s "$B/api/runs" > before.json
curl -s "$B/api/kkd/summary?run_id=RUN-002&unit_id=HQ-CIB" > before-summary.json
curl -s "$B/api/kkd/issues?run_id=RUN-002&limit=200" > before-issues.json

# 2. Откат всего: схема и данные
docker compose run --rm migrate rollback --tag=v0-empty < /dev/null
docker compose exec -T db psql -U kkd -d kkd -c "\dt" < /dev/null     # только databasechangelog и databasechangeloglock
docker compose exec -T db psql -U kkd -d kkd -c "select count(*) from databasechangelog" < /dev/null     # 0: откат убрал и строку метки
curl -si "$B/api/runs"     # HTTP 503 и {"error":{"code":"DB_NOT_READY",...}}

# 3. Повторный накат. Сервис перезапускать не нужно. Каждый diff ничего не печатает: ответы те же
docker compose run --rm migrate update < /dev/null
wait_runs
curl -s "$B/api/runs" | diff before.json -
curl -s "$B/api/kkd/summary?run_id=RUN-002&unit_id=HQ-CIB" | diff before-summary.json -
curl -s "$B/api/kkd/issues?run_id=RUN-002&limit=200" | diff before-issues.json -
```

Данные вернулись, если все три `diff` ничего не напечатали. Файлы `before*.json` остаются в папке проекта, Git их не видит.

Оговорки:

- `docker compose down -v` — это сброс базы, а не откат.
- После отката обычный `docker compose up` или `docker compose up -d app` снова запускает контейнер `migrate`, и он накатывает всё обратно. Это тот же повторный накат, что и `migrate update`.
- Между откатом и накатом в журнале `db` есть строки `ERROR:  relation "kkd_run" does not exist`, а в журнале `app` строка `База не готова`. Это не сбой: сервис раз в такт ищет прогоны, а таблиц пока нет.
- Повторный `rollback --tag=v0-empty` без наката завершится ошибкой `Could not find tag`. Это ожидаемо: откатывать уже нечего, а метка ушла вместе с остальным.
- После правки файлов в `db/changelog` нужна пересборка: `docker compose build migrate`.
- Команды `psql` рассчитаны на значения по умолчанию. Если в `.env` заданы другие `POSTGRES_USER` или `POSTGRES_DB`, их нужно подставить.

## Установка на отдельный стенд

`docker compose` поднимает всё на одной машине. На стенд со своей базой PostgreSQL те же образы ставятся по отдельности, а подключение к базе передаётся только переменными окружения. Нужен PostgreSQL 15 или новее и пользователь — владелец базы, права суперпользователя не нужны. Стартовые данные входят в миграции и тоже попадают на стенд.

Команды для Git Bash и Linux. Вместо `<...>` нужно подставить данные стенда. Адрес базы должен быть виден из контейнера: `localhost` внутри контейнера — это сам контейнер. Порт 8080 должен быть свободен: проект из compose перед этим остановить.

```bash
# Образы: миграции и сервис
docker build --target migrate -t kkd-migrate .
docker build --target runtime -t kkd-service .

# Подключение к базе стенда
DB_URL=jdbc:postgresql://<хост>:<порт>/<база>
DB_USER=<пользователь>
DB_PASSWORD=<пароль>
mig() { docker run --rm -e LIQUIBASE_COMMAND_URL="$DB_URL" -e LIQUIBASE_COMMAND_USERNAME="$DB_USER" -e LIQUIBASE_COMMAND_PASSWORD="$DB_PASSWORD" -e LIQUIBASE_COMMAND_CHANGELOG_FILE=changelog/db.changelog-master.yaml kkd-migrate "$@"; }
B=http://127.0.0.1:8080
wait_runs() { for i in $(seq 1 60); do curl -sf --max-time 5 "$B/api/runs" | grep -q '"id":"RUN-002","status":"completed"' && return 0; sleep 1; done; echo "не дождались RUN-002"; return 1; }

# 1. Накат, затем сервис
mig update
docker run -d --name kkd-service -p 8080:8080 -e DB_URL="$DB_URL" -e DB_USER="$DB_USER" -e DB_PASSWORD="$DB_PASSWORD" kkd-service
wait_runs

# 2. Откат: сервис работает и отвечает 503
mig rollback --tag=v0-empty
curl -si "$B/api/runs"

# 3. Повторный накат
mig update
wait_runs
curl -s "$B/api/runs"
```

Убрать сервис: `docker rm -f kkd-service`. Как и в compose, перед откатом команды ждут `completed`: сразу после старта сервис считает прогоны. Что происходит с данными на каждом шаге: [раздел 9.4 `design.md`](specs/design.md#94-что-происходит-с-данными), остальное о стенде: [раздел 9.5](specs/design.md#95-установка-на-отдельный-стенд).

## API

Методов три, все GET. Подробный контракт: [раздел 8 `design.md`](specs/design.md#8-контракт-api).

Метода со списком подразделений нет, поэтому коды стартовых данных записаны здесь. Скрипт сквозной проверки сверяет обе таблицы с базой и ответами API.

### Методы и параметры

| Метод | Параметр | Обязателен | Значения |
|---|---|---|---|
| `GET /api/runs` | нет параметров | | Список прогонов, новые сверху |
| `GET /api/kkd/summary` | `run_id` | да | Код прогона |
| | `unit_id` | да | Код подразделения, считается вместе с дочерними |
| `GET /api/kkd/issues` | `run_id` | да | Код прогона |
| | `unit_id` | нет | Код подразделения, включает дочерние |
| | `rule_code` | нет | `GOAL_NO_OWNER`, `GOAL_NO_KR`, `KR_WEIGHTS_SUM`, `CASCADE_NO_PARENT`, `KR_NO_TARGET`, `KR_STALE_PROGRESS`. Код выключенного правила даёт пустой список |
| | `severity` | нет | `critical`, `major`, `minor` |
| | `limit` | нет, по умолчанию 20 | Целое от 1 до 200 |
| | `offset` | нет, по умолчанию 0 | Целое от 0 до 2147483647 |

Примеры для порта по умолчанию:

```bash
curl -s "http://127.0.0.1:8080/api/runs"
curl -s "http://127.0.0.1:8080/api/kkd/summary?run_id=RUN-002&unit_id=HQ-CIB"
curl -s "http://127.0.0.1:8080/api/kkd/issues?run_id=RUN-002&unit_id=CIB-NORTH&severity=major&limit=5&offset=0"
```

### Ошибки

Формат один: `{"error": {"code": "...", "message": "..."}}`. Сообщения на русском, без стека и имён классов.

| Статус | `code` | Когда |
|---|---|---|
| 422 | `INVALID_PARAM` | Нет обязательного параметра, пустое или неверное значение, неизвестный `rule_code`, испорченная строка запроса: неверная запись `%XX` или параметр без имени, например `=1` |
| 404 | `RUN_NOT_FOUND`, `UNIT_NOT_FOUND`, `NOT_FOUND` | Неизвестный прогон, подразделение или путь |
| 405 | `METHOD_NOT_ALLOWED` | `POST`, `PUT`, `PATCH`, `DELETE`, например `POST /api/runs` |
| 400 | `REQUEST_NOT_SUPPORTED` | Испорченный адрес: неверная запись `%XX` после `;` в пути, например `/api/runs;x=%zz` |
| Другой клиентский статус Spring MVC, например 406 | `REQUEST_NOT_SUPPORTED` | Прочие неподдерживаемые запросы |
| 409 | `RUN_FAILED`, `RUN_IN_PROGRESS` | `summary` или `issues` для прогона `failed` или `running` |
| 503 | `DB_NOT_READY` | База недоступна или таблиц нет: например, между откатом и накатом |
| 500 | `INTERNAL_ERROR` | Непредвиденная ошибка сервера |

Порядок проверок: форма параметров (422), прогон (404), подразделение (404), состояние прогона (409). В ответе одна ошибка, первая найденная.

## Архитектура решения

### Слои и путь запроса

```text
HTTP-запрос
  → api: RunController, KkdController. Параметры разбирает RequestParser, ошибки оформляет ApiExceptionHandler
  → service: RunQueryService, SummaryService, IssueService
  → repository: RunRepository, UnitRepository, SnapshotRepository, IssueRepository. Только SQL через JdbcTemplate
  → PostgreSQL
```

Расчёты лежат в пакете `ru.kkd.domain`. Он не знает о Spring, SQL и HTTP. Контроллеры отделены от сервисов и от доступа к данным. Все пакеты и классы: [раздел 10 `design.md`](specs/design.md#10-структура-кода).

**Почему Spring Boot 3.5.16.** Задание требует Spring Boot 3, поэтому взята последняя ветка 3.x, хотя у неё уже нет бесплатной поддержки.

### Где живёт логика правил

Логика правил лежит в пакете `ru.kkd.domain.rules`. На каждое правило свой класс: `GoalNoKrRule`, `KrWeightsSumRule`, `CascadeNoParentRule`, `KrStaleProgressRule`. Все они реализуют интерфейс `Rule`, а запускает их `RuleEngine`.

```java
List<Issue> RuleEngine.check(Snapshot snapshot, RuleCatalog catalog)
```

- **Что получает:** `Snapshot` с целями и КР на дату прогона и `RuleCatalog` с включёнными правилами и их важностью.
- **Что возвращает:** список найденных проблем `Issue` в постоянном порядке.
- **Что делает:** оставляет только активные цели (`GoalRow.isActive()`, `status = 'active'`, срок не важен), применяет включённые правила и сортирует результат.
- **Почему отдельно:** так просит задание. Компонент не ходит в базу и ничего не знает об API, поэтому границы правил проверяются обычными тестами без базы и HTTP. Данные ему загружает и результат записывает `RunProcessor`.

### Какие правила выбраны и почему

Набор дал все три уровня важности, оба типа объекта, две числовые границы для тестов и проверку каскада. Коды `GOAL_NO_OWNER` и `KR_NO_TARGET` есть в справочнике `kkd_rule` с `enabled = false`, но не считаются и в метрики не входят.

| Правило | Важность, объект | Нарушение | Не нарушение |
|---|---|---|---|
| `GOAL_NO_KR` | critical, цель | В снимке нет ни одного КР этой цели | Есть хотя бы один КР |
| `KR_WEIGHTS_SUM` | major, цель | КР есть, и сумма весов не равна 100 ровно или один из весов пуст. Нарушают 99.99, 100.01, 33.3 × 3. Сравнение `BigDecimal.compareTo`, допуска нет | 100, 100.00, 33.4 + 33.3 + 33.3. Цель без КР: её отмечает `GOAL_NO_KR` |
| `CASCADE_NO_PARENT` | major, цель | Уровень не `department`, и родитель не указан, не найден в снимке или не выше по уровню | Уровень `department`: у него нет вышестоящей цели. Закрытый родитель, родитель из другой ветки подразделений, прыжок через уровень |
| `KR_STALE_PROGRESS` | minor, КР | От `fact_updated_on` до `snapshot_date` больше 45 дней. 46 уже нарушает | Ровно 45 дней. Пустая дата. Дата позже снимка |

### Как устроен прогон

Прогон запускается появлением строки со статусом `running` в таблице `kkd_run`: из стартовых данных или вставкой SQL. Метода API для запуска нет, GET-методы прогоны не считают и ничего не пишут.

1. `RunPoller` работает внутри сервиса, раз в такт ищет строки `running`. Такт задаёт `KKD_RUN_POLL_MS`, по умолчанию 2000 мс.
2. `RunProcessor` считает прогон одной транзакцией: снимает снимок, если его ещё нет, вызывает `RuleEngine`, выбирает базу сравнения через `BaseRunSelector`, пишет строки `kkd_issue` и ставит `completed`.
3. При ошибке логики или данных прогон получает `failed`. Повторов нет. Если база не готова, прогон остаётся `running` и берётся снова в следующем такте.

**Снимок** — это копия всех целей и КР, в том числе закрытых, на дату прогона: таблицы `goal_snapshot` и `key_result_snapshot`. Снимки нужны, потому что `goal` и `key_result` хранят только текущее состояние. По ним нельзя честно посчитать прошлые значения метрик, а правка цели меняла бы ответы по старым прогонам. Возраст факта считается только от `snapshot_date`, поэтому ответы не зависят от дня запуска.

Стартовые прогоны идут тем же путём: миграция создаёт строки `running` со снимками, а проблемы считает сервис.

### Как считаются метрики

Метрики считает `MetricCalculator` при запросе из снимка и проблем прогона, в базе они не хранятся.

Обозначения: `A` активные цели ветки, `P` разные `goal_id` среди проблем ветки, `N` активные цели ветки не уровня `department`, `C` проблемы `CASCADE_NO_PARENT` в ветке.

| Метрика | Вид | Формула | `value` равен `null`, когда | Лучше, когда |
|---|---|---|---|---|
| `clean_goals_share`, доля корректных целей, % | качественная | `(A − P) × 100 ÷ A` | `A = 0` | больше |
| `issues_total`, найдено проблем, шт. | количественная | Число строк проблем ветки | никогда | меньше |
| `cascade_coverage`, покрытие каскадом, % | качественная | `(N − C) × 100 ÷ N` | `N = 0` | больше |

- **Дочерние подразделения.** Всё считается по ветке: подразделение и все его потомки на любую глубину (`UnitTree.branchOf`). Числитель и знаменатель общие, свои цели родителя входят, среднего долей нет.
- **Проблема КР** делает цель некорректной. Цель с тремя проблемами считается один раз.
- **Округление.** `BigDecimal`, `RoundingMode.HALF_UP`, 1 знак: 1 из 16 даёт 6.3, 2 из 3 даёт 66.7. Округляет только `MetricCalculator`.
- **Дельта метрики** считается в `MetricComparison` из уже округлённых значений: 56.5 − 62.7 = −6.2.
- **`trend`.** `same` при дельте 0, `better` при изменении в лучшую сторону с учётом направления метрики, иначе `worse`. Если `value` или `previous` равен `null`, то и `trend` равен `null`.

Подробности и особые случаи: [раздел 5 `design.md`](specs/design.md#5-метрики).

### Как считается дельта

Проблема та же самая, если совпали правило и объект: ключ `IssueKey` — это пара `(rule_code, object_id)`. Текст `details` в ключ не входит. Счётчики считает `DeltaCalculator`.

| Счётчик | Условие | К какой ветке относится |
|---|---|---|
| `new` | Пара есть в текущем прогоне и нет в базе сравнения | По `unit_id` текущей строки |
| `persisting` | Пара есть в обоих | По `unit_id` текущей строки |
| `resolved` | Пара есть в базе сравнения и нет в текущем | По `unit_id` прошлой строки |

**База сравнения.** Последний `completed` с меньшим `(snapshot_date, id)`, упавшие и выполняющиеся пропускаются. Её выбирает `BaseRunSelector` при завершении прогона и записывает `RunProcessor` в `kkd_run.compared_to_run_id`. API читает это поле и заново базу не выбирает.

**Первый прогон.** Сравнивать не с чем, поэтому `compared_to`, все `previous`, `delta`, `trend` и три счётчика равны `null`, а не 0. Так же выглядит прогон, у которого все прошлые упали.

**Что значит `resolved`.** Пара пропала по любой причине, причину модуль не различает. Например, в `RUN-002` проблема `KR_STALE_PROGRESS:KR-14-1` считается `resolved`, хотя факт никто не обновил: цель `G-14` просто закрыли.

**Почему `resolved` нет в списке проблем.** `GET /api/kkd/issues` отдаёт строки одного прогона, а исправленной проблемы в нём уже нет. Поэтому `resolved` — это только счётчик в `GET /api/kkd/summary`. Чтобы увидеть такую проблему, можно сравнить списки двух прогонов: у той же проблемы тот же `id`.

Вернувшаяся проблема снова `new`, потому что сравнение идёт только с одним прогоном. Подробности, в том числе перенос цели между подразделениями: [раздел 7 `design.md`](specs/design.md#7-сравнение-прогонов).

### Проверка третьим прогоном

Откат удаляет прогоны, добавленные руками, поэтому эту проверку выполняют после цепочки. Блок сам поднимает проект, если он остановлен: например, скрипт из раздела [«Сквозная проверка»](#сквозная-проверка) в конце его останавливает. Функция `wait_runs` та же, что в разделе [о цепочке](#накат--откат--повторный-накат).

```bash
B=http://127.0.0.1:${APP_PORT:-8080}
wait_runs() { for i in $(seq 1 60); do curl -sf --max-time 5 "$B/api/runs" | grep -q '"id":"RUN-002","status":"completed"' && return 0; sleep 1; done; echo "не дождались RUN-002"; return 1; }
docker compose up -d
wait_runs
docker compose exec -T db psql -U kkd -d kkd -c "INSERT INTO kkd_run (id, snapshot_date) VALUES ('RUN-003', '2026-11-02')" < /dev/null
sleep 3   # прогон считается за один такт, до 2 секунд
curl -s "$B/api/runs"
curl -s "$B/api/kkd/summary?run_id=RUN-003&unit_id=HQ-CIB"
curl -s "$B/api/kkd/issues?run_id=RUN-003&rule_code=KR_STALE_PROGRESS"
```

| Прогон | Дата | `issues_total` | База | `new` | `persisting` | `resolved` | Новая проблема |
|---|---|---:|---|---:|---:|---:|---|
| `RUN-003` | 2026-11-02 | 12 | `RUN-002` | 1 | 11 | 0 | `KR_STALE_PROGRESS:KR-03-1` |

Данные никто не менял: факту `KR-03-1` просто стало 52 дня при пороге 45. Если `RUN-003` уже вставлен, для сравнения ответов до и после отката сначала нужен сброс: `docker compose down -v` и `docker compose up -d`. Без сброса откат и накат тоже пройдут и удалят `RUN-003`, но первый `diff` цепочки напечатает разницу: в `before.json` этот прогон есть, а после наката его нет.

## Сквозная проверка

```bash
bash scripts/check-chain.sh
```

Скрипт поднимает проект с нуля и сверяет настоящий запуск со спецификацией: все числа и таблицы этого README, контракт API, цепочку миграций, третий прогон и граничные случаи. Что он проверяет по шагам: [раздел 11.2 `design.md`](specs/design.md#112-сквозная-проверка-scriptscheck-chainsh).

**Он начинается и при успехе заканчивается сбросом базы проекта: `docker compose down -v`.** При успехе в конце строка с числом проверок и временем. При сбое скрипт печатает, что проверялось, ожидание и факт, завершается с кодом не 0, а база остаётся для разбора.

## Решения там, где задание молчит

Самые важные. Все решения с причинами: [раздел 12 `design.md`](specs/design.md#12-ключевые-решения).

- **Запуск прогона.** Вставка строки `running` в `kkd_run`. В задании только три GET, а расчёт внутри GET заставил бы его писать в базу.
- **Таблицы снимков** сверх перечня задания. Настоящие прошлые значения требуют прошлых знаменателей.
- **Результаты стартовых прогонов считает сервис.** Миграция не пишет `kkd_issue`, поэтому компонент правил работает не только в тестах.
- **Уровень цели.** Поле `level`: `department`, `unit`, `employee`. Правило каскада говорит о «вышестоящем уровне», значит, уровень надо где-то хранить. Верхний уровень не проверяется.
- **Активная цель.** `status = 'active'`, срок не важен: просроченная цель в работе, пока её не закрыли.
- **Пустые значения.** Пустой вес нарушает `KR_WEIGHTS_SUM`, потому что подсчёт как 0 спрятал бы дефект. Пустая дата факта не нарушает `KR_STALE_PROGRESS`: возраст неизвестен.
- **Незавершённый прогон.** `summary` и `issues` отвечают 409. В `GET /api/runs` у него `totals` равен `null`, а не 0: проверки не было.
- **Миграции в отдельном контейнере.** Перезапуск сервиса не накатывает изменения обратно и не прячет откат. Между откатом и накатом API отвечает 503 `DB_NOT_READY`.

Что сознательно не делали: [раздел 13 `design.md`](specs/design.md#13-что-сознательно-не-делаем).

## Известные ограничения

Самые важные. Полный список: [раздел 14 `design.md`](specs/design.md#14-известные-ограничения).

- Прогоны запускаются только вставкой SQL. Еженедельного расписания нет: задание называет его планом.
- Прогоны, добавленные руками, не переживают откат: повторный накат возвращает только `RUN-001` и `RUN-002`.
- `failed` не повторяется: нужна новая строка прогона с новым идентификатором. Прогон без снимка с датой раньше последнего завершённого сразу получает `failed`.
- Дерево подразделений одно на все прогоны. Реорганизация дерева пересчитает прошлые значения родителя.
- Цикл целей через уровень `department` не виден правилу каскада.
- SQL репозиториев не покрыт JUnit: ошибку в запросе покажет только `scripts/check-chain.sh`.
- Ошибки до Spring MVC не в едином формате: на испорченный адрес, например `/api/%2F`, и на строку запроса с пробелом или буквами не ASCII без кодирования `%XX` Tomcat сам отвечает 400 с HTML.
